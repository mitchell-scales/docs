## Transformations List

- **Transformation** — the transformation's name.
- **Lifecycle** — current stage, colour-coded to the freshness of the data.
- **Activities** — the activities this transformation powers.
- **Last Processed** — when the transformation last ran.
- **Actions** — row-level actions for the transformation

### **Mapping**

This is how your SQL dataset maps to the standard activity format.

<Frame>
  ![Image](/images/image-4.png)
</Frame>

<Card title="Activity" icon="bolt" horizontal>
  Choose whether the activity comes from a source column or a fixed value. Selecting **Column** lets one column distinguish between activities — for example, a column separating email opens and clicks generates a `click` activity and an `open` activity.
</Card>

<Card title="Customer Columns" icon="user" horizontal>
  Map either `customer`, `anonymous_customer_id`, or both — for example, an email for known customers and an anonymous ID for unknown ones.
</Card>

<Card title="Required Columns" icon="asterisk" horizontal>
  Mappings required before validation can pass: **Activity Id**, a unique identifier per row, and **Timestamp**, in timestamp format.
</Card>

<Card title="Additional Columns" icon="plus" horizontal>
  Optional standard fields for richer activity data — **Revenue Impact** and **Link**.
</Card>

<Card title="Feature Columns" icon="table-columns" horizontal>
  Select any columns to pack into `feature_json` on the compiled query. These features are created across every activity generated by this transformation.
</Card>

### Processing Configuration

<Columns cols={3}>
  <Card title="Schedule" icon="clock">
    Controls how often the transformation processes source data — **Update Every** sets the cadence. **Delete recent days** controls whether recent rows are replaced on each run, with a configurable **Delete last N days** and **Delete frequency**.
  </Card>

  <Card title="Identity" icon="fingerprint">
    Controls how the transformation participates in customer identity workflows — **Identity resolution**, the **Identity source** column, whether it **Creates mapping** or **Uses mappings**, and whether it **Aliases customer**.
  </Card>

  <Card title="Data Rules" icon="sliders">
    Overrides default stream behaviour for edge-case source data — **Allow future data** (e.g. scheduled revenue timestamped ahead of now), **Never delete rows**, **Delete customers**, and **Set data cutoff**.
  </Card>
</Columns>

<Warning>
  Certain configuration combinations surface a cost warning — for example, creating identity mappings and deleting recent rows together is expensive, since changing mappings requires identity resolution to be undone and redone.
</Warning>

### Activities

Lists the activities this transformation powers, or shows that none are linked yet.

### Debug Summary

Internal processing state for debugging — draft dataset, generated activities, last and next run times, identity source, feature columns, and next state.

### Production Query

Links directly to the query currently running in production for this transformation.

### Data Updates

A chart of update runs, switchable between **Rows**, **Cost**, and **Duration**.

### Test Status

Whether tests have run, broken down by check type, and whether the transformation is ready to push to production.

## Creating Multiple Activities from One Source

When one transformation needs to produce several activities, which approach to use depends on whether those activities share the same feature columns.

### Same Feature Columns

<Steps>
  <Step title="Add an activity column to the dataset">
    Create a SQL dataset with a column whose values name the activity — for example, `click`, `open`, `sent`.
  </Step>
  <Step title="Point the activity name at that column">
    On the transformation, set the activity name to reference that column instead of a fixed value.
  </Step>
  <Step title="One transformation generates every activity">
    The transformation creates one activity per distinct value in the column, using the value as the activity name.
  </Step>
  <Step title="Pick the shared feature columns">
    The feature columns you select are generated across every activity this transformation produces — for example, a shared `campaign_id` column means click, open, and sent will all carry the same feature columns.
  </Step>
</Steps>

### Different Feature Columns

<Steps>
  <Step title="Pre-filter the dataset into parent tabs">
    Create a SQL dataset with one tab per activity — for example, separate tabs for click, open, and sent.
  </Step>
  <Step title="Point a transformation at each tab">
    Use the transformation's tab selector to target a specific parent tab.
  </Step>
  <Step title="Create one transformation per tab">
    Each parent tab gets its own transformation, since the feature columns differ between activities.
  </Step>
  <Step title="Pick feature columns per transformation">
    Since each tab has its own transformation, each can select a different set of feature columns — one transformation might pack in a different set of columns than another.
  </Step>
</Steps>
